# 深度与因果点图蒸馏：三人并行排期与算力预算

## 0. 结论卡

当前 P0 项目的推荐配置为：

- **团队：3 人**；
- **基准周期：8 周**；
- **快速周期：6 周**，风险较高；
- **保守周期：11～12 周**；
- **推荐数据规模：30 万唯一目标帧**；
- **数据比例：40% 仿真 GT + 40% DA3/Pi3X 教师数据 + 20% 真机数据**；
- **推荐算力：2 张卡持续生产数据，4 张 80GB 卡负责训练与消融**；
- **完整 P0 预算：约 800～1500 A100-80GB GPU 小时**；
- **高速存储：最低 1TB，推荐 2TB NVMe；若保存完整点图，推荐 2～4TB**。

推荐的人员结构：

| 人员 | 主职责 | 核心交付物 |
|---|---|---|
| A：数据负责人 | 仿真 GT、DA3/Pi3X Teacher Cache、真机数据、数据审计与版本管理 | 可复现的 Smoke、Pilot 和 Full 数据版本 |
| B：训练负责人 | 学生结构、Geo-Adapter、因果核心、输出头、损失函数和主训练 | 主模型、训练配置、checkpoint 与部署导出 |
| C：评测与第二训练负责人 | 可微 SVD/IRLS、评测系统、消融、错误分析和性能测试 | Oracle、自动评测榜、消融结果与最终报告 |

项目的关键路径是：

```text
坐标系、K 和深度定义冻结
→ GT 点图经过 SVD 能恢复 GT pose
→ Smoke 训练通过
→ 全量 Teacher Cache 完成并审计
→ Full 主训练
→ 消融与复现
→ 冻结最佳 checkpoint
→ 一次性测试集评测
```

> 最大工期风险通常不是学生模型训练，而是 Pi3X 严格因果标签生成、坐标/尺度错误导致的 Cache 返工，以及真机标定或补采。

---

## 1. 本计划对应的固定蒸馏架构

### 1.1 教师模型

- **DA3Metric-Large**：提供逐帧米制 Z-depth；
- **Pi3X causal-prefix**：提供 local points、world points 和 point confidence；
- **仿真器/传感器 GT**：提供深度、相机内参、相机位姿、有效区域和静态区域；
- 教师只在离线数据生产阶段运行，部署时全部移除。

### 1.2 学生模型

```text
RGB_t + K_network + bounded state
        ↓
DINOv2-B/14
        ↓
Geo-Adapter / 少量 Geo-LoRA
        ↓
4-layer Causal Geo-Temporal Core
        ↓
Local Point Head
+ World Point Head
+ Confidence / Static-Valid Head
        ↓
Frozen weighted SE(3) SVD
+ 3 × Huber IRLS
```

学生部署输出：

- `local_points_cam`；
- `world_points_segment`；
- `point_confidence / static_valid_mask`；
- `depth_metric = local_points_cam[..., 2]`；
- 由固定求解器派生的 `T_frontend_c2w`、相对位姿和 tracking diagnostics。

### 1.3 估算前提

本计划的基准算力按以下条件估算：

| 项目 | 基准设定 |
|---|---|
| 唯一目标帧总量 | 30 万帧 |
| 数据比例 | 40% 仿真 GT、40% DA3/Pi3X、20% 真机 |
| 网络输入分辨率 | 336 × 504 |
| Pi3X 因果窗口 | 8 帧，只保留窗口最后一帧的正式标签 |
| 学生参数量 | 约 101M，其中 DINOv2-B/14 约 86M |
| 训练精度 | BF16 混合精度 |
| 学生训练数据遍历 | 约 30～35 次有效遍历 |
| DINO 策略 | 前期冻结；后期最多解冻顶部少量 block |
| SVD 输入点数 | 每帧空间均匀采样约 4K～16K 点 |

算力数字是工程预算，不是厂商性能承诺。正式 Full 预算必须在 1K～5K 帧的 Smoke/Pilot 上实测吞吐后重新校准。

## 2. 三人详细分工

## 2.1 A：数据负责人

### 持续负责

- 定义并维护统一数据 schema；
- 固定 RGB、K、Z-depth、pose 和 point-map 的坐标约定；
- 生成 Habitat 或 Isaac Sim 仿真数据；
- 运行 DA3Metric-Large；
- 运行 Pi3X causal-prefix；
- 完成 clip 共享尺度和首帧 world gauge 对齐；
- 生成 valid/static/occlusion/confidence；
- 构建 Smoke、Pilot、Full 三层数据版本；
- 维护 scene-disjoint 的 Train/Validation/Test；
- 维护 manifest、checksum、教师版本和预处理版本；
- 输出数据质量报告及坏样本列表。

### A 不负责

- 不独立决定学生模型结构；
- 不根据某次训练结果静默修改已发布的 Teacher Cache；
- 不把 Test 场景补入 Train；
- 不在没有版本号的情况下覆盖旧标签。

### A 的核心验收

- 任意样本都能追溯到原始数据、教师 checkpoint 和生成参数；
- `K_original → crop/resize → K_network` 可复算；
- local/world 点图同像素网格、同单位；
- 每个 segment 首帧 gauge 正确；
- GT/教师点图经过统一 SVD 接口能够产生合理位姿；
- 数据分桶比例和有效像素统计可复现。

## 2.2 B：训练负责人

### 持续负责

- 实现 DINOv2-B/14 接口；
- 实现 Geo-Adapter 与可选 Geo-LoRA；
- 实现 4 层因果几何时序核心；
- 实现 local/world/confidence 三个正式输出头；
- 实现 metric depth/local/world/structure/pose/temporal/confidence 损失；
- 维护训练配置、随机种子、优化器和学习率计划；
- 执行 Tiny overfit、Pilot 和 Full 主训练；
- 记录训练曲线、checkpoint、代码提交和数据版本；
- 导出最终 FP16/BF16 部署模型。

### B 不负责

- 不绕过点图增加正式 direct-pose 主输出；
- 不允许训练期和部署期使用不同求解器；
- 不在未经过数据负责人发布的临时目录上启动 Full；
- 不以训练 loss 单项决定模型优劣。

### B 的核心验收

- Tiny set 可以明显过拟合；
- `depth = local Z` 始终成立；
- world point 不跨 segment 混用 gauge；
- 长序列状态大小保持 O(1)；
- 主训练可以断点续训并完整复现；
- 最佳 checkpoint 在冻结 Validation 规则下选出。

## 2.3 C：评测与第二训练负责人

### 持续负责

- 实现 confidence-weighted Kabsch/SVD；
- 强制 `det(R)=+1`；
- 实现固定 3 次 Huber IRLS；
- 实现 solver residual、inlier ratio、coverage 和 weak/lost；
- 实现 depth、point-map、ATE、RPE、长跨度漂移指标；
- 构建 GT point-map → solver 的 Oracle 测试；
- 构建前缀因果性、重投影、尺度和退化测试；
- 建立自动验证榜和错误案例分层；
- 运行第二 seed、关键消融和部署性能测试；
- 负责最终锁定测试集评测。

### C 不负责

- 不根据 Test 结果反向调整训练配方；
- 不使用 Sim(3) 或 GT median scale 美化米制主结果；
- 不把 direct-pose 结果作为点图求解失败后的正式 fallback；
- 不只报告 ATE 而忽略深度、点图、尺度和 tracking 状态。

### C 的核心验收

- Oracle 点图能恢复 GT pose；
- 测试训练与部署使用同一 solver ID；
- 评测结果能按数据桶、场景、运动类型和困难条件拆分；
- confidence 和真实残差具有合理相关性；
- 最终测试只在模型与配方冻结后运行一次。

## 3. 基准排期：8 周

| 周次 | A：数据线 | B：训练线 | C：评测/第二训练线 | 周末闸门 |
|---|---|---|---|---|
| **W1** | 冻结 schema、坐标轴、K、Z-depth、pose、segment gauge；准备三桶最小样本 | 搭建 DINOv2-B/14、Geo-Adapter、4 层因果核心和三输出头 | 实现 weighted SE(3) SVD、3×Huber IRLS 和基础指标 | 单 batch 完整前向、损失、反向均通过 |
| **W2** | 生成约 1% Smoke 数据，覆盖前进、旋转、小基线、reset 和退化场景 | 过拟合 32～64 个 clip，完成短训练 | 完成 pose Oracle、重投影、因果泄漏、退化和 NaN 测试 | Smoke 七项硬闸门全部通过 |
| **W3** | 扩展至 5%～10% Pilot；统计 DA3/Pi3X 冲突、尺度和 confidence | 跑 GT-only、输出蒸馏、输出+结构化蒸馏三条短线 | 建立自动验证榜、错误分层和教师上限 | 冻结主要损失与标签融合规则 |
| **W4** | 开始按 scene shard 生产 Full；持续校验全量 40/40/20 数据 | 在 Pilot 上冻结窗口长度、batch、学习率和显存方案 | 完成无蒸馏基线、吞吐测试和显存分析 | Full 数据与训练配置冻结 |
| **W5** | 完成并锁定 Full Cache v1；冻结 Train/Val/Test | 启动第一次 Full 主训练 | 持续评估 checkpoint、scale drift、world gauge 和 weak/lost | 主训练收敛方向正常，无系统性标签故障 |
| **W6** | 只允许隔离坏样本和定向回补；发布明确的新 patch 版本 | 根据预设规则执行一次修正重训 | 跑 DA3-only、Pi3X-only、去结构、去时序、去 solver 等关键消融 | 选出 1～2 个候选模型 |
| **W7** | 输出数据卡、质量审计和已知缺陷 | 冻结配方后运行第二 seed 或最终长训 | 完成分域评测、长序列漂移、真机、速度和显存测试 | 最佳 checkpoint 冻结 |
| **W8** | 归档数据、教师版本和 manifest | 导出最终学生模型及推理配置 | 对锁定 Test 只评测一次，整理精度、速度、消融和失败案例 | P0 正式交付 |

## 4. Smoke 硬闸门

以下项目未全部通过，禁止启动全量 Pi3X 标签生成和 Full 主训练。

| 编号 | 必须通过的检查 | 失败通常意味着什么 |
|---|---|---|
| S1 | 仿真 GT local/world 点图经固定 SVD 能恢复 GT pose | 坐标轴、变换方向、单位或对应关系错误 |
| S2 | SVD 结果始终满足 `det(R)=+1` | 旋转反射修正错误 |
| S3 | Segment 首帧满足 `T=I` 且 `local≈world` | world gauge 或首帧定义错误 |
| S4 | 无噪 GT 重投影误差低于约 0.5 像素 | K、crop/resize 或 Z-depth 定义错误 |
| S5 | 32～64 个 clip 能明显过拟合且无 NaN | 模型、损失、mask 或梯度链路错误 |
| S6 | 序列末尾追加未来帧，不改变已有前缀学生输出 | 存在未来帧泄漏或错误缓存 |
| S7 | 40/40/20 采样、有效像素归一化和 confidence 权重正确 | DataLoader 或损失归一化错误 |
| S8 | 退化输入能返回 weak/lost，而不是异常的大位姿 | 求解器退化判断和置信度机制错误 |

Smoke 的目标不是获得高精度，而是证明：

```text
坐标正确
+ 标签正确
+ 因果正确
+ 损失可优化
+ solver 可审计
```

## 5. 数据与训练并行方式

## 5.1 三层数据版本

```text
Smoke v0：约 1%
    ↓ 通过全部几何闸门
Pilot v1：约 5%～10%
    ↓ 冻结标签定义、损失与吞吐估计
Full v2：100%，按 scene 分片生产
```

W3 以后允许数据生产和训练并行，但必须满足：

- 训练只读取已经发布并校验的 shard；
- 每个 shard 都有独立 manifest 和 checksum；
- 记录原始数据 ID、教师 checkpoint、代码版本和生成配置；
- 记录 `preprocess_id`、`K_network`、clip scale 和 world gauge；
- Cache 变更必须发布新版本，不能原地覆盖；
- Validation/Test 从 W1 开始锁定；
- Full 训练配置只允许读取一个明确的 Cache 版本集合。

## 5.2 推荐的GPU调度

使用 6 张 GPU 时：

| 阶段 | 数据生产卡 | 训练卡 | 评测/消融卡 |
|---|---:|---:|---:|
| W1～W2 | 1～2 | 2 | 1～2 |
| W3～W4 | 2 | 2～3 | 1 |
| W5 | 0～1 | 4 | 1 |
| W6～W7 | 0～1 | 3～4 | 1～2 |
| W8 | 0 | 1 | 1～2 |

如果只有 4 张 80GB GPU：

- W1～W4：2 张生成数据，1 张 Smoke/Pilot 训练，1 张评测；
- W5 以后：Teacher Cache 完成后，4 张全部转入 Full 主训练；
- 第二 seed 与消融需要串行，8 周计划会更紧；
- 推荐减少非关键消融，不要削减 Smoke 检查。

## 6. 算力预算

## 6.1 单次完整流程

下表表示“一次教师标签生产 + 一次学生完整训练”的预算，单位为 A100/A800-80GB GPU 小时。

| 唯一帧规模 | 仿真 GT | DA3 标签 | Pi3X 严格因果标签 | 学生训练 | 单次总计 |
|---:|---:|---:|---:|---:|---:|
| 10 万 | 1～3 | 1～3 | 36～72 | 60～135 | **100～210 GPUh** |
| **30 万** | **2～8** | **3～7** | **107～215** | **180～400** | **290～630 GPUh** |
| 100 万 | 8～25 | 9～23 | 356～715 | 590～1330 | **960～2090 GPUh** |

表中已经粗略包含约 20% 的 I/O、验证和标签对齐余量，但没有包含完整的多 seed 与大量消融。

## 6.2 完整P0项目预算

| 唯一帧规模 | 一次主流程 | 加入 Smoke、Pilot、一次重训和关键消融 |
|---:|---:|---:|
| 10 万 | 100～210 GPUh | 250～500 GPUh |
| **30 万** | **290～630 GPUh** | **800～1500 GPUh** |
| 100 万 | 960～2090 GPUh | 2500～5000 GPUh |

当前 P0 推荐 30 万帧，而不是直接上 100 万帧。原因是标签融合、world gauge 和因果窗口都需要先经过真实实验验证；如果标签定义存在错误，100 万帧 Cache 的返工成本很高。

## 6.3 学生训练阶段的算力占比

| 阶段 | 主要内容 | 建议占学生训练预算 |
|---|---|---:|
| S1 | Metric depth + local point 预热 | 10%～15% |
| S2 | 启用 causal core + world point | 20%～25% |
| S3 | 加入 solver-in-the-loop、pose 与刚体一致性 | 25%～30% |
| S4 | 40/40/20 联合微调 | 30%～35% |
| S5 | 量化校准、导出和短微调 | 5%～10% |

> 3 次 Huber IRLS 本身不是主要算力瓶颈，前提是从点图中均匀采样 4K～16K 点，而不是对全部约 16.9 万像素进行完整反向求解。

## 7. Pi3X 因果标签为什么是主要成本

严格因果窗口长度为 8 时，每个正式目标帧需要输入 8 张历史图像：

```text
Pi3X 实际图像输入量
= 教师目标帧数 × 因果窗口长度
= 0.4 × 唯一帧总数 × 8
```

以 30 万唯一帧为例：

```text
12 万 Pi3X 目标帧 × 8
= 96 万次图像输入
```

Pi3X 官方 A800-80GB、BF16、336×504 的大规模 benchmark 约为 2.8 images/s，峰值显存约 40.6GB。但该结果是大规模连续输入吞吐；长度为 8 的小窗口还会受到窗口启动、重复编码、加载和落盘影响，不能直接把 2.8 images/s 当作项目承诺吞吐。

Pi3X 官方 VO 代码默认使用 16 帧 chunk 和 6 帧 overlap。它能降低重复计算，但 chunk 内较早帧可以看到后续图像，因此不能未经审计就当作严格 causal-prefix 标签。

### 安全的降本方式

1. **Pi3X stride=2**：每两帧生成一个 Pi3X 锚点，Pi3X 成本约减半；
2. **Pi3X stride=4**：每四帧生成一个锚点，Pi3X 成本约降至四分之一；
3. DA3 仍逐帧生成米制深度；
4. 非锚点帧通过相邻监督和时序损失参与训练；
5. 后续若实现并验证真正的 causal attention/state reuse，再重新生成更密标签。

P0 推荐先使用：

```text
DA3：逐帧
Pi3X：stride=2
```

这样通常比直接把 Pi3X 窗口从 8 缩短到 2 更稳妥。

## 8. 硬件建议

## 8.1 最低可运行配置

- 2 × 48GB GPU；
- 一张用于教师数据生产，一张用于 Smoke/Pilot 训练；
- 适合 10 万帧以内的验证；
- 数据与训练并行能力有限；
- 日历周期预计延长到约 10～14 周；
- 不适合同时跑第二 seed 和多项消融。

## 8.2 推荐配置

```text
数据节点
  2 × A100-80GB
  或 2 × 48GB 专业卡
  用于 Pi3X、DA3 和仿真数据生成

训练节点
  4 × A100/H100-80GB
  用于 Full 主训练、第二 seed 和消融

主机与存储
  32～64 CPU cores
  256GB RAM
  1～2TB 本地高速 NVMe
  10GbE 或更高带宽的共享存储
```

## 8.3 100万帧配置

- 推荐 8 × 80GB GPU；
- 高速存储至少 3～4TB；
- Teacher Cache 建议分节点、分 scene 并行生产；
- 只有在 30 万帧 P0 已证明有效后再扩展。

## 9. 存储预算

## 9.1 完整点图缓存

若保存以下全部内容：

- RGB；
- FP16 depth；
- FP16 local XYZ；
- FP16 world XYZ；
- FP16 confidence；
- valid/static masks；

则每帧约占 2.7～3.5MB。

| 数据规模 | 完整缓存 |
|---:|---:|
| 10 万帧 | 270～350GB |
| 30 万帧 | 0.8～1.05TB |
| 100 万帧 | 2.7～3.5TB |

## 9.2 紧凑缓存

推荐 Full 阶段只保存：

- RGB；
- FP16 depth；
- K；
- 每帧/每窗口 pose 或确定性变换参数；
- uint8 confidence；
- valid/static masks；
- scale、gauge 和预处理元数据。

训练时通过确定性函数重建 local/world points。

| 数据规模 | 紧凑缓存 |
|---:|---:|
| 10 万帧 | 65～95GB |
| 30 万帧 | 195～285GB |
| 100 万帧 | 650～950GB |

考虑原始数据、两个 Cache 版本、shard、日志和 checkpoint 后：

- 10 万帧：建议至少 500GB；
- 30 万帧：最低 1TB，推荐 2TB；
- 100 万帧：建议至少 3～4TB。

## 10. 三档周期

## 10.1 快速档：6周

适用条件：

- 教师环境已经完整可用；
- Habitat/Isaac 资产已经准备好；
- 真机原始数据和标定已经完成；
- GPU与高速存储可独占；
- 只跑一个 seed 和 4～5 个关键消融；
- 接受较高返工风险。

压缩方式：

```text
W1～W2：Smoke
W3：Pilot + 并行生产 Full Cache
W4～W5：Full 主训练 + 最小消融
W6：冻结、锁测、导出
```

## 10.2 基准档：8周

推荐采用。

包含：

- 完整 Smoke 硬闸门；
- 5%～10% Pilot；
- 一次 Full 主训练；
- 一次有依据的修正重训；
- 第二 seed 或最终复现训练；
- 核心教师、结构和 solver 消融；
- 仿真、教师域和真机分域评测；
- 数据卡、模型卡和失败案例。

## 10.3 保守档：11～12周

适用于：

- 坐标或标定可能返工；
- 真机需要补采；
- Pi3X吞吐尚未实测；
- 需要2～3个随机种子；
- 需要更完整的运动、材质和场景分层；
- 还要进行量化、端侧测速和部署优化。

建议额外预留：

- 1周：坐标/K/深度或 Teacher Cache 返工；
- 1周：真机补采和标定；
- 1～2周：多个 seed、部署与量化。

## 11. 关键风险与缓冲

| 风险 | 可能影响 | 预防措施 | 建议缓冲 |
|---|---|---|---:|
| Pi3X严格因果标签吞吐不足 | Full Cache延迟 | W2用1K～5K帧实测；优先stride=2 | 3～7天 |
| 坐标轴或c2w/w2c方向错误 | 全量Cache失效 | GT point→SVD Oracle作为硬闸门 | 3～7天 |
| K在resize/crop后错误 | 深度反投影和位姿系统性错误 | 保存K_original、K_network和preprocess_id | 2～5天 |
| DA3和Pi3X尺度冲突 | 米制平移不稳定 | clip共享尺度、教师一致性过滤 | 2～5天 |
| 真机时间同步/标定不可靠 | Sim-to-Real结论失真 | 先采小批标定验证，再扩采 | 3～7天 |
| confidence全部趋低 | solver无有效点 | NLL + coverage + 最低有效点约束 | 2～4天 |
| world gauge漂移 | 长序列VO失败 | 首帧I、segment reset和multi-span评测 | 3～7天 |
| 训练与部署solver不一致 | 线下好、部署差 | 固定唯一solver_id | 1～3天 |

## 12. 建议保留的最小消融

时间紧张时，至少保留下列实验：

| 实验 | 目的 |
|---|---|
| 仅仿真 GT | 建立干净监督基线 |
| GT + DA3 | 验证米制深度教师价值 |
| GT + Pi3X | 验证多帧 local/world 教师价值 |
| GT + DA3 + Pi3X | 验证联合教师主方案 |
| 去掉结构/刚体一致性 | 验证结构化蒸馏价值 |
| 去掉 causal core | 验证 world point 是否真正依赖时序 |
| 未加权 SVD vs confidence-weighted SVD | 验证置信度作用 |
| weighted SVD vs weighted SVD + 3×IRLS | 验证鲁棒求解器作用 |
| 加入20%真机前后 | 验证Sim-to-Real收益 |

这些实验应尽量复用同一份 Teacher Cache，避免重复生成教师标签。

## 13. 每周例会需要回答的问题

每周只围绕以下问题检查状态：

1. 本周使用的是哪个数据版本、教师版本和代码提交？
2. 当前是否仍满足严格 causal-prefix？
3. GT point-map Oracle 是否持续通过？
4. local/world 是否同网格、同单位、同 gauge？
5. 当前主要错误来自 depth、local point、world point、confidence 还是 solver？
6. 学生改善是否同时反映在点图与 SVD pose 上？
7. 是否出现数据标签被静默修改的情况？
8. GPU 利用率、数据吞吐和落盘速度是否符合 W2 实测预算？
9. 下一周是否会触发全量 Cache 或 Full 重训等高成本动作？
10. 高成本动作是否已经通过对应阶段闸门？

## 15. 最终推荐

当前最合理的执行口径是：

```text
3人
+ 30万唯一目标帧
+ 8周
+ 40%仿真GT / 40% DA3+Pi3X / 20%真机
+ 2张GPU持续生产数据
+ 4张80GB GPU负责训练、复现和消融
+ 1～2TB高速NVMe
+ 800～1500 A100 GPU小时项目预算
```

执行原则：

> 在 W2 Smoke 全部通过之前，不启动全量 Pi3X 标签生产；在 Pilot 冻结标签定义之前，不启动 Full 主训练；在模型和配方冻结之前，不查看最终 Test 结果。
